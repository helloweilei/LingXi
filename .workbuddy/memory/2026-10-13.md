## 修复：后一章与前一章完全连不上（连贯性问题）
现象：逐章生成正文时，每章像"另起炉灶"，与上一章毫无关联。

根因（AiService.writeChapter 上下文不足）：
1. 只注入「上一章结尾 800 字」——AI 只看到末尾几百字，**不知道上一章整体发生了什么**；
2. **上一章的大纲完全没注入**（本章大纲注入了，上一章的没有）；
3. 更早章节的剧情毫无信息，"每章像新故事"；
4. 提示词只说"注意衔接"，没有把衔接列为最高优先级，也无可执行的衔接清单。

改动（AiService.writeChapter）：
- 上一章上下文从 800 → **2000 字**（PREV_TAIL_CHARS）
- 新增注入【上一章】区块：章号 + 标题 + **上一章大纲**(900字) + 上一章结尾原文
  （区块名明确写"务必从这段之后无缝衔接，不要另起炉灶"）
- 新增 `appendRecentOutlinesBrief()`：回溯前 3 章（RECENT_OUTLINE_CHAPTERS）注入
  【前文剧情回顾】（每章 260 字，RECENT_OUTLINE_CHARS）；
  **降级策略**：某章无大纲时退化为该章正文尾部 160 字，保证至少有"前情"
- 第一章特判：无上一章时明确告知"这是全书第一章，没有上一章可承接"
- 任务提示词新增 **第 0 条【最高优先级】开篇必须与上一章结尾无缝衔接**：
  第一段从上一章结尾的时点/地点/人物状态直接接续、不重新开场、承接未完成的冲突或动作、
  人物位置/情绪/随身物品保持一致；终章分支同样补了衔接要求
- 文风指令第 3 条强化为"保持情节连贯：人物动机、称谓、时间线与前文一致"

验证：前端 build 通过（纯后端改动）；需重启后端并**重新生成受影响章节**才能看到效果。

## 修复：正文生成到一半被截断（句子断在半截）★重要
现象：生成的正文停在半句话（如"火焰卷过"），后续没有内容。

### 根因（两个叠加）
1. `max-output-tokens: 8192` 是**硬顶**：中文约 1 字 ≈ 1~1.5 token，8192 ≈ 5500~6000 字，
   章节目标字数一旦超过必被中途切断；
2. 每章目标字数 =总目标/章节数**无上限**，例如 30万字/5章 = 每章 6 万字，
   远超单次输出能力 → 必然截断。

### 改动
1. **提高 token 上限**：`max-output-tokens` 8192 → **16384**（application.yml + AiProperties 默认值）
2. **每章字数封顶**：`perChapterTargetWords()` 增加 `Math.min(words, MAX_CHAPTER_WORDS=6000)`
   与 16384 token 对齐（留余量）；另加 `isPerChapterCapped()` 供提示用户调整章节数
3. **自动续写（根治）**——新增 `completeIfTruncated(Novel, User, content)`：
   - `looksTruncated()`：结尾无句末标点（。！？…」』》）等）或末段 <12 字 → 判为截断
   - 最多续写 `MAX_CONTINUE_ROUNDS=3` 轮，每轮从断点接续（`continueChapterPrompt`：
     明确"直接从最后一句之后接着写，不要重复、不要另起炉灶"），超时 `CONTINUE_TIMEOUT=5min`
   - `writeChapterAndSave` 落库前调用；续写异常只warn 不阻断（至少保存已有内容）
   - **`AutoWriteService` 也接入**（流水线自行 save 不走 writeChapterAndSave，之前会漏保护）
4. 提示词补强：【字数】段追加"本章必须一次性写完并写完整：结尾必须收束完整，绝不能停在半句话上"
5. 新增 `AiServiceTruncationTest` 固化截断判定规则（含截图中的真实案例"火焰卷过"）

**经验**：LLM 长文本生成必须做「截断检测 + 自动续写」，不能假设一次调用能写完；
且业务侧的"目标字数"必须与模型输出能力（max_tokens）对齐，否则必然产出废稿。

## 修复：续写提示词把 Java 代码原样输出给模型
现象：截断续写触发时，提示词里出现 `""" + tail(existing, max: 1500) + """`、
`本次续写约 """ + (1000 + round * 500) + """ 字` 等代码片段。

根因：Java 文本块（`"""`）中**以 + 开头的行属于块内容，不是拼接运算符**。
原写法 `""" + tail(x) + """` 在文本块内部换行续写时，
`tail(existing, 1500) + """` 这段被当成了字面量文本，于是拼进了提示词。

修法：改用 formatted() 一次性拼好，**绝不在文本块内部写 + 表达式**：
```java
String promptTemplate = """
        【任务】...
        【已写到的内容（结尾）】
        %s
        ...
        5. 本次续写约 %d 字。
        """;
return baseContext(novel) + promptTemplate.formatted(tail(existing, 1500), 1000 + round * 500);
```
已用脚本模拟拼接验证：结果为「本次续写约 1500 字」，无任何代码符号残留；
并全量grep 确认其余 4 处 .formatted 用法均为「块内只有占位符、块外 formatted」的正确模式。

**Java 文本块铁律**：块内不要写 + 表达式；要么整块用 %s/%d 占位 + .formatted()，
要么在块外用 + 拼接。多行文本 + 插值一律走 formatted()。

## 修复：「生成正文」实为续写，导致新章与前章割裂 ★重要 UX 问题
现象：点「生成正文」后，新内容从**上次生成的旧稿**接着写，与第一章完全割裂。
用户原话：「添加功能之前一定要从用户的角度考虑，不要出现迷惑行为。」

根因：`AiService.writeChapter` 无条件执行 `currentTail = tail(chapter.getContent(), 1200)`，
并提示词声明"从当前结尾自然续写"。而自动创作流水线本来就会先建**空章节**，
所以原写法为流水线"复用"了章节内容 —— 但导致前端「生成正文」也变成续写，
语义与按钮字面含义完全相反。**这是典型的为了复用而牺牲语义。**

### 修复：生成(重写) 与 续写(追加) 彻底分离
- `AiService.writeChapter(..., boolean appendExisting)`：
  - false（默认）：`currentTail = ""`，**整章重写**，忽略本章旧稿，从上一章结尾重新写
  - true：带入本章旧稿尾部，从断点续写
- `AiService.writeChapterAndSave(..., boolean appendExisting)`：
  - 重写模式：生成结果直接覆盖；仅当被截断时才 completeIfTruncated 补全
  - 续写模式：**原文 + "\n\n" + 新内容** 拼接保存（只增不重）；不做截断续写
- `AiController`：
  - `/chapters/{id}/write` → appendExisting=false（整章重写）
  - **新增 `/chapters/{id}/write-continue`** → appendExisting=true（接着写）
- `AutoWriteService` 显式传 false（流水线处理空章节，行为不变）

### 前端（NovelOutlinesTab.tsx）
- `writeOne(item, append=false)` 按 append 切换 URL 与标题/成功文案
- 新增 `continueWrite(item)`：无正文时 message.info 引导改用「生成正文」
- 「更多」菜单：写正文项在已有正文时文案变「整章重写」；新增「从当前内容接着写」
  （`disabled: !hasContent`，无正文时禁用避免迷惑）；用 divider 与「删除大纲」分隔
- 覆盖确认文案改为：「将基于本章大纲**整章重写**（忽略当前正文，从上一章结尾重新写）。
  旧内容会自动留版本快照，可回滚；也可以取消后用「更多 → 从当前内容接着写」在原文后追加。」
- 「一键生成正文」tooltip 说明「已有正文会被重写，旧内容可回滚」

**产品原则（后续务必遵守）**：一个入口的语义必须与按钮文字一致；
为复用代码而改变语义是错的——宁可多写一个方法/端点，也不要让用户猜按钮是干什么的。
